# 백엔드 프로젝트 진행 순서

서비스 아이디어를 실제 백엔드 구현으로 옮길 때 참고하는 기본 흐름입니다. 프로젝트마다 순서가 조금씩 달라지며, ERD와 API 명세는 구현 중에도 계속 수정될 수 있습니다.

## 전체 흐름

```text
문제와 요구사항 확인
        ↓
MVP 범위 결정
        ↓
사용자 흐름·IA·UI 확인
        ↓
도메인과 용어 정리
        ↓
데이터 흐름·ERD·API 초안
        ↓
아키텍처와 구현 범위 결정
        ↓
기능 구현 및 연동
        ↓
테스트·배포·검증
```

## 1. 문제와 요구사항 확인

### 확인할 내용

- 누가 사용하는 서비스인가?
- 어떤 문제를 해결하는가?
- 사용자가 완료해야 하는 핵심 행동은 무엇인가?
- 프로젝트의 제한 시간과 기술 조건은 무엇인가?

### 결과물

- 서비스 설명
- 사용자 시나리오
- 기능 요구사항

## 2. MVP 범위 결정

### 확인할 내용

- 없으면 서비스가 성립하지 않는 기능은 무엇인가?
- 데모에서 반드시 보여줘야 하는 흐름은 무엇인가?
- 이번 프로젝트에서 제외할 기능은 무엇인가?

### 결과물

- 핵심 기능 목록
- 구현 제외 목록
- 완료 기준

## 3. 사용자 흐름·IA·UI 확인

백엔드는 화면을 그대로 구현하는 역할은 아니지만, 각 화면에서 어떤 데이터를 조회하고 저장하는지 알아야 합니다.

### 확인할 내용

- 사용자가 어떤 순서로 이동하는가?
- 버튼을 누르면 어떤 데이터가 바뀌는가?
- 화면마다 서버에서 필요한 값은 무엇인가?

### 결과물

- 사용자 흐름도
- IA
- 화면별 필요한 데이터 목록

## 4. 도메인과 용어 정리

팀원이 같은 단어를 같은 의미로 사용하도록 정리합니다.

### 정리할 내용

- 핵심 도메인
- 상태값과 상태 변경 규칙
- 비슷하지만 다른 용어
- 생성·조회·수정의 주체

### 결과물

- 용어 사전
- 도메인 목록
- 상태 흐름

## 5. 데이터 흐름과 ERD 설계

### 진행 순서

1. 저장할 데이터를 나열한다.
2. 테이블과 컬럼을 정한다.
3. PK와 FK를 정한다.
4. 관계와 제약조건을 정한다.
5. 샘플 데이터로 주요 흐름을 검증한다.

### 결과물

- ERD
- 테이블 설명
- 샘플 데이터

## 6. API 명세 작성

### 진행 순서

1. 화면과 기능에서 API 후보를 찾는다.
2. 도메인별로 중복 기능을 합친다.
3. Method와 Endpoint를 정한다.
4. Request와 Response를 정한다.
5. 실패 상황과 상태 코드를 정한다.

### 결과물

- API 목록
- 요청·응답 명세
- 에러 응답 규칙

## 7. 아키텍처와 구현 방식 결정

### 확인할 내용

- 서버와 데이터베이스 구성
- 인증과 권한
- 파일 저장 방식
- 외부 API 연동
- 동기·비동기 처리
- 배포 환경

### 결과물

- 아키텍처 그림
- 패키지 구조
- 환경변수 목록
- 기술 결정 기록

## 8. 작업 분배와 구현

### 권장 방식

- 화면 단위가 아니라 도메인과 API 책임을 명확히 나눈다.
- 한 기능을 DB부터 API 응답까지 먼저 완성한다.
- 구현 전 브랜치, 커밋, PR 규칙을 합의한다.
- API 변경 사항은 바로 공유 문서에 반영한다.

### 결과물

- 작업 목록과 담당자
- 구현 코드
- API 테스트 결과

## 9. 연동과 테스트

### 확인할 내용

- 정상 요청과 응답
- 잘못된 요청
- 데이터가 없는 경우
- 중복 요청
- 인증 실패
- 외부 서비스 실패

### 결과물

- 테스트 목록
- 오류 기록
- 수정 내역

## 10. 배포와 검증

### 확인할 내용

- 배포 환경에서 API가 동작하는가?
- 환경변수와 보안 설정이 분리되어 있는가?
- 로그로 오류 원인을 확인할 수 있는가?
- 실제 사용자 흐름을 처음부터 끝까지 실행할 수 있는가?

### 결과물

- 배포 주소
- 실행 방법
- 데모 시나리오
- 남은 문제 목록

## 해커톤에서 최소한으로 준비할 것

- [ ] 핵심 사용자 흐름 1개
- [ ] 핵심 기능과 제외 기능
- [ ] ERD
- [ ] API 목록과 핵심 응답 예시
- [ ] 더미 데이터 또는 시드 데이터
- [ ] 역할 분담
- [ ] 프론트엔드 연동 확인
- [ ] 실패했을 때 보여줄 대체 데모

## 자주 발생하는 실수

- UI가 완성될 때까지 백엔드 설계를 시작하지 않는다.
- 모든 화면마다 별도 API를 만든다.
- ERD 컬럼과 API 필드의 의미가 서로 다르다.
- 핵심 기능보다 로그인, 알림, 설정을 먼저 구현한다.
- 성공 상황만 만들고 빈 데이터와 오류 상황을 확인하지 않는다.
- 문서를 한 번 작성한 뒤 변경 사항을 반영하지 않는다.
